# ADR-0001: Design principles for a flat Cypress course repo (Phase 8)

## Status

Accepted

## Context

`udemy_cypress_13.6.6` is a Udemy course's Cypress E2E test-automation teaching repo: 19 numbered spec files (`Tc01`–`Tc19`, one gap at `Tc16`), fixtures, a 4-class Page Object Model used by exactly one spec, a custom command (`cy.conduItLogin`), Docker wrapper, and one CI workflow. There is no application under test living in this repo — every spec drives a public third-party demo site directly. The repo's own "product" is the test code itself.

Phase 8 (structure-architect) must assess standard software-design principles (DRY, KISS/YAGNI, SOLID, Clean/Hexagonal, DDD, EDA, Modular monolith, GoF) and decide which apply, which are `n/a`, and what — if anything — changes.

## Decision

### DRY (login duplication) — deferred, not applied

11 of 19 specs repeat the same raw Conduit-login selector sequence inline (`cy.get('a[href="#login"')` / email / password / submit) instead of reusing the `cy.conduItLogin` custom command or the Page Object Model introduced later in the same course.

This is real duplication, but collapsing it onto one reusable path would erase the course's deliberate progression: each lesson demonstrates the *next* authoring technique (inline → fixture → custom command → POM). The duplication *is* the teaching artifact. Per KISS/YAGNI, no speculative abstraction is introduced in this phase. The decision is revisited only if a future phase already needs to touch those specs for another reason.

Recorded in `docs/ARCHITECTURE.md` "Design principles applied (Phase 8)".

### All other principles — n/a, documented with reasons

- **SOLID**: only 4 trivial Page Object wrapper classes, each single-responsibility; no class has "several reasons to change."
- **Clean / Hexagonal**: no owned external system to swap behind an interface; third-party sites are consumed, not integrated with.
- **DDD**: no domain complexity or invariants belong to this repo; its domain is "how to write Cypress tests," already the structure.
- **EDA**: no async reactions or cross-service integration; the repo runs to completion and exits.
- **Modular monolith**: single-purpose test tooling; no internal module boundaries worth formalizing.
- **GoF**: Page Object Model is already in use and correctly scoped; it is a test-automation pattern, not a GoF pattern. No other GoF pattern is applicable.

No code changes result from this ADR.

## Consequences

- **Positive**: The repo stays focused on its actual purpose (teaching Cypress) without speculative architecture that would never be exercised.
- **Negative**: The 11-spec login duplication remains; a future maintainer who wants a single reusable login path must make the deliberate call to collapse the pedagogy, not an accidental byproduct of this phase.
- **No behavior change**: no spec, fixture, page object, support file, plugin, Dockerfile, workflow, or Makefile target is modified by this decision.
